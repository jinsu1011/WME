# 세션(AI) 역할 분담

여러 대화를 동시에 쓰면 빨라지지만, **대화끼리는 서로의 기억을 공유하지 않는다.**
그래서 규칙이 없으면 서로 다른 결정을 내리고 같은 파일을 덮어쓴다.
아래 두 가지만 지키면 그 사고가 나지 않는다.

1. **폴더 소유권** — 세션마다 건드릴 폴더가 정해져 있다. 남의 폴더는 읽기만 한다.
2. **시작 전 읽기 / 끝나고 쓰기** — 시작할 때 `PROJECT_HEAD.md` 와 `기획/PROGRESS.md` 를 읽고,
   끝날 때 `기획/PROGRESS.md` 를 갱신한다.

## 세션 4개

| 세션 | 담당 | 쓰기 가능 | 읽기만 |
|---|---|---|---|
| **HEADER** | 기획·문서·의사결정·발표 | `PROJECT_HEAD.md`, `기획/`, `제출/` | 전부 |
| **FRONT** | 화면 | `web/frontend/` | `기획/설계/` |
| **BACK** | API·DB·LLM 연결 | `web/backend/`, `data/local/` | `web/frontend/src/types`, `src/api` |
| **SENSOR** | 펌웨어·데이터 수집·이상 탐지 모델 | `hardware/`, `data/` (local 제외) | 전부 |

**LLM 교육 피드백은 BACK 담당이다.** API 키를 들고 호출하는 쪽이 서버이기 때문에,
LLM을 따로 떼면 같은 FastAPI 파일을 두 세션이 건드리게 된다.
SENSOR 세션의 AI는 **센서 이상 탐지 모델**만 맡는다.

## 결정은 HEADER에서만

"서비스명 바꾸자", "이 기능 빼자", "구조를 이렇게 바꾸자" 같은 판단은 HEADER에서 내리고
`PROJECT_HEAD.md` 에 적는다. 다른 세션에서 그런 얘기가 나오면 **거기서 결정하지 말고
HEADER로 가져온다.** 세션마다 다른 결정을 내리는 게 이 방식의 유일한 실패 원인이다.

## 순서

동시에 4개를 돌릴 필요는 없다. 실제로는 이 순서다.

```
HEADER (기획·문서)  ─── 계속 열어두기
   │
   ├─ FRONT   ← 지금 여기. 작업량 제일 많음
   ├─ BACK    ← FRONT에서 답변 제출이 되면 시작
   └─ SENSOR  ← 센서 도착하면 시작
```

## 두 노트북을 번갈아 쓸 때

- **프롬프트에 절대 경로를 적지 않는다.** 노트북마다 경로가 다르다.
  프로젝트 폴더를 열고 시작하면 상대 경로로 충분하다.
- **`node_modules` 는 동기화하지 않는다.** 노트북마다 `npm install` 을 따로 한다.
- 작업을 끝내고 다른 노트북으로 옮기기 전에 **반드시 `기획/PROGRESS.md` 를 갱신**한다.
  그게 두 노트북 사이의 유일한 인수인계 수단이다.
- 같은 파일을 두 노트북에서 동시에 열지 않는다. 클라우드 동기화는 충돌 사본을 만든다.

## 세션 프롬프트

| 파일 | 용도 |
|---|---|
| `HEADER.md` | 기획·문서·발표 |
| `FRONT.md` | 화면 작업 |
| `BACK.md` | API·DB·LLM |
| `SENSOR.md` | 펌웨어·데이터·이상 탐지 |

새 대화 첫 메시지에 해당 파일 내용을 붙여넣는다.

**더 간단한 방법**: 프로젝트 루트의 `이어서작업.md` 에 역할별 짧은 붙여넣기 블록과
현재 진행 상황이 함께 있다. 다른 노트북에서 이어받을 때는 그 파일을 쓴다.
이 폴더의 파일들은 각 역할의 **상세 규칙서**이고, 세션이 시작하면서 읽는다.
