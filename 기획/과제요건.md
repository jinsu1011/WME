## 5. HEADER 결정 (2026-09-14, 과제 요건 대응)

사용자 지시: **3D 장비 뷰와 센서는 유지한다.** PPT(발표자료)는 나중에 정한다.

| # | 결정 | 이유 |
|---|---|---|
| R1 | 제출물을 **DBML · OpenAPI YAML · 개요 PDF** 로 만든다. 기존 `DB설계.md`·`API명세서.md` 는 원본 자료로 유지 | 파일 형식·이름이 평가 조건 |
| R2 | **3D·센서는 유지하되 "핵심 기능을 보여주는 화면"으로 문서화**한다. 센서는 **선택 입력 장치**, 키보드가 기본 | 기능 명확성 점수 + "과도한 범위" 감점 회피 |
| R3 | 센서 연결의 **예외 흐름**(미지원 브라우저·미연결·수신 없음·키보드 전환)을 UI 흐름도에 넣는다 | 세부 기준 "예외·오류 시나리오" 가점 |
| R4 | 센서 전용 API 가 없는 이유(Web Serial 브라우저 직통)와 실시간 기록(WebSocket)은 **YAML description + 고려사항**에 적는다 | OpenAPI 는 WebSocket 을 표현하지 않는다. 누락으로 보이지 않게 |
| R5 | **로그인 API·비밀번호 해시를 설계에 넣는다(`[설계]` 표시).** 시연 앱은 구현하지 않고 데모 전환 유지 | 로그인 화면에 대응 API 가 없으면 "UI 필요 API 누락". 평가는 설계이므로 정당. 구현했다고 쓰지 않는다 |
| R6 | **제출용 ERD(DBML)는 논리 설계로 정규화한다** — 시연 앱의 JSON 컬럼 10개에 든 화면 데이터를 테이블·컬럼으로 드러낸다(19테이블, 그룹 4개). M:N: 배정↔단계, 시도↔루브릭, 시도↔확인 항목, 피드백↔근거 구간. **API 응답 구조는 그대로**(배열 = 하위 테이블 행). 시연 앱 저장 위치는 각 테이블 Note·`화면설계.md` 4절에 매핑 | 데이터 모델 20점 기준 "UI 의 모든 데이터 필드 · PK/FK · 1:N·M:N · 타입·제약". JSON 한 칸이면 그림에서 필드가 안 보인다. *(9/14 밤 1차안 "note 로 풀기"를 사용자 위임으로 HEADER 가 변경)* |
| R7 | 액터는 **신입사원 · 매니저 2종 + 외부 시스템 2종(LLM, 교육용 모형 컨트롤러)** | 범위를 키우지 않는다. 과정 등록·배정은 범위 밖으로 명시 |
| R8 | 에러 코드는 **서버가 실제로 내는 것(404·409·422·503) + 설계 로그인의 401** 만 적는다 | 내지 않는 코드를 적으면 API 와 구현 불일치 |
| R9 | 3D·센서·LLM 에 **새 기능을 더하지 않는다.** 문서가 끝난 뒤에만 센서 측정 | 점수는 문서에서 나온다 |

## 6. 코드 대조에서 찾은 UI ↔ API 불일치 (2026-09-14)

| # | 내용 | 조치 |
|---|---|---|
| M1 | `PATCH /api/enrollments/{id}/progress` 를 **어떤 화면도 부르지 않는다** → 진도(`stepsCompleted`)가 시드에서 안 바뀐다 | FRONT — 실습 단계 완료 시 호출 |
| M2 | `POST /api/attempts/{id}/feedback/viewed` 를 **프론트가 부르지 않는다** | FRONT — 결과 화면에서 피드백이 보이면 호출 |
| M3 | 로그인 화면(아이디·비밀번호 입력)에 대응 API 없음 | R5 로 설계에 추가 |
