# 실습 유형 설계 — 범용성 구조

> **HEADER 확정 문서.** FRONT와 BACK이 이 문서의 규격을 그대로 따른다.
> 여기 적힌 이름·값·구조를 각자 바꾸지 않는다. 바꿔야 하면 HEADER로 가져온다.
>
> 확정: 2026-09-13

## 1. 왜 하는가

지금 범용성은 반쪽이다.

| | 상태 |
|---|---|
| 업종 문구 | ✅ `tenant.ts` · `courses.ts` 로 분리됨 |
| 실습 유형 | ❌ 정렬 하나에 고정 |
| **채점 규칙** | ❌ **파이썬 코드에 박혀 있다** (`scoring.py`) |

루브릭 *문장*은 데이터인데 *채점 방법*은 코드다. 그래서 과정이 바뀌면 코드를 고쳐야 한다.
**이 문서의 목적은 채점을 데이터로 내리고, 실습 유형을 갈아끼울 수 있게 만드는 것이다.**

## 2. 층 나누기

```
플랫폼 층 (이미 범용, 건드리지 않는다)
  사용자 · 과정 · 배정 · 시도 / 루브릭 4기준 0·1·2 /
  피드백 구조 / 담당자 집계 / 시계열·구간 기록

실습 층 (유형별로 갈아끼운다)
  조작 화면 · 측정 지표 · 분석기 · 채점 규칙(데이터)
```

## 3. `exercise_type`

`courses` 테이블에 컬럼 하나를 추가한다. 이것이 유일한 스키마 변경이다.

```sql
exercise_type TEXT NOT NULL DEFAULT 'alignment'
  CHECK (exercise_type IN ('alignment','judgment'))
```

| 값 | 실습 | 조작 |
|---|---|---|
| `alignment` | 마스크·웨이퍼 정렬 | 키보드 / 모형 컨트롤러 |
| `judgment` | 상황 판단·확인 순서 | 조작 없음. 순서 배열 + 서술 |

응답에는 `exerciseType` 으로 나간다.

## 4. `scoring_metrics` — 채점기와 도메인을 끊는 지점

**분석기가 `summary_json` 안에 `scoring_metrics` 라는 평평한 딕셔너리를 만든다.**
채점기는 이 딕셔너리만 본다. 그래서 채점기는 정렬이 뭔지, 포토공정이 뭔지 모른다.

```json
"scoring_metrics": {
  "finalPositionError": 3.83,
  "finalRotationError": 0.868,
  "overshootCount": 2,
  "convergenceOrder": "rotation_first",
  "axisInterference": false,
  "reportedOrderMismatch": false,
  "converged": true,
  "answerLength": 62,
  "rotationOutsideComfort": false,
  "rotationOutsideRange": false
}
```

`modifiers.when` 이 불리언만 받기 때문에, 숫자 비교가 필요한 조건은
**분석기가 미리 불리언 지표로 만들어 둔다.** 규칙 문법을 늘리는 대신 지표를 늘린다.
(`rotationOutsideComfort` / `rotationOutsideRange` 가 그 예다. BACK 제안, HEADER 승인)

값은 숫자 · 불리언 · 문자열만 쓴다. 중첩하지 않는다.

기존 `summary_json` 의 다른 필드(`final_dx`, `path_analysis` 등)는 **그대로 둔다.**
화면과 문서가 이미 쓰고 있다. `scoring_metrics` 는 옆에 추가되는 것이다.

## 5. `scoring` — 과정 데이터에 들어가는 채점 규칙

`courses.content_json.scoring` 에 배열로 둔다. 배열 길이는 루브릭 개수와 같다.

### 5.1 `threshold` — 숫자 지표

작은 값이 좋은 지표를 기준으로 한다. `max` 는 "이 값 이하면 이 점수".
위에서부터 평가하고 처음 맞는 것을 쓴다. 마지막 항목에는 `max` 를 두지 않는다(나머지 전부).

```json
{
  "criterion": 0,
  "metric": "finalPositionError",
  "type": "threshold",
  "unit": "px",
  "levels": [
    { "max": 2.4,  "score": 2, "reason": "허용 범위 안에 여유 있게 들어왔습니다." },
    { "max": 4.0,  "score": 1, "reason": "허용 범위 경계에 걸쳐 있습니다." },
    { "max": 10.0, "score": 1, "reason": "허용 범위를 조금 벗어났습니다." },
    {              "score": 0, "reason": "허용 범위 밖에서 확정했습니다." }
  ]
}
```

큰 값이 좋은 지표는 `"direction": "higher"` 를 두고 `min` 을 쓴다.

### 5.2 `categorical` — 범주형 지표

```json
{
  "criterion": 1,
  "metric": "convergenceOrder",
  "type": "categorical",
  "map": { "position_first": 2, "rotation_first": 2, "together": 1, "unknown": 0 },
  "reasons": {
    "position_first": "기록상 한 축씩 순서대로 정리했습니다(위치 → 회전).",
    "rotation_first": "기록상 한 축씩 순서대로 정리했습니다(회전 → 위치).",
    "together": "위치와 회전이 비슷한 시점에 정리됐습니다.",
    "unknown": "허용 범위 안으로 들어오지 않아 조정 순서를 읽을 수 없습니다."
  }
}
```

`map` 에 없는 값이 오면 0점으로 하고 이유에 "판정할 수 없습니다"를 쓴다.

### 5.3 `modifiers` — 조건부 보정 (선택)

두 방식만 지원한다. 더 늘리지 않는다.

```json
"modifiers": [
  { "when": "axisInterference", "adjust": -1,
    "reason": "한 축을 맞추는 동안 다른 축이 함께 움직인 구간이 있습니다." },
  { "when": "reportedOrderMismatch", "capAt": 1,
    "reason": "적어 낸 순서와 기록이 다릅니다." }
]
```

- `when` 은 `scoring_metrics` 의 **불리언 지표 이름**이다. 참일 때만 적용한다
- `adjust` 는 점수를 더한다(음수면 뺀다). `capAt` 은 그 값을 넘지 못하게 한다
- 적용 후 0~2 범위로 자른다. 여러 개면 배열 순서대로 적용한다

### 5.4 `reason` 문구에 값 끼워넣기

`{metric}` 형태를 쓰면 채점기가 값으로 바꾼다.

```
"reason": "목표를 지나친 구간이 {overshootCount}회 있습니다."
```

없는 지표 이름이면 바꾸지 않고 그대로 둔다(문장이 깨지지 않게).

## 6. 정렬 실습(`alignment`)의 채점 규칙

지금 `scoring.py` 에 코드로 박혀 있는 것을 데이터로 옮긴 것이다.
**점수 결과가 지금과 같아야 한다.** 옮긴 뒤 시드 12건을 재채점해 값이 바뀌지 않는지 확인한다.

| 기준 | metric | 방식 |
|---|---|---|
| 0 정렬 정확도 | `finalPositionError` (+ 회전은 modifier) | threshold. 허용치의 60% 안쪽이면 2 |
| 1 조정 순서 | `convergenceOrder` | categorical + `axisInterference`(−1) + `reportedOrderMismatch`(capAt 1) |
| 2 보정 효율 | `overshootCount` | threshold (0회=2, 1~2회=1, 3회 이상=0) |
| 3 설명·기록 | `answerLength` | threshold, `direction: higher` |

## 7. 두 번째 실습 — `judgment` 유형

### 7.1 과정

| | |
|---|---|
| id | `defect-report` (카탈로그에 이미 "준비 중"으로 있다) |
| 제목 | 공정 이상 상황 보고 — 무엇부터 확인할 것인가 |
| exerciseType | `judgment` |
| availability | `available` 로 바꾼다 |
| 예상 시간 | 15분 |

**조작이 없다. 센서도 캔버스도 필요 없다.** 읽고 판단하고 적는 것이 전부다.
그래서 "우리가 가르치는 것은 손재주가 아니라 관찰과 판단"이라는 포지셔닝을 직접 증명한다.

### 7.2 화면 흐름

```
상황 카드 + 관측값 표를 읽는다
  → 확인 항목 5개의 순서를 정한다
  → 왜 그 순서인지 적는다
  → 제출 → 정렬 실습과 똑같은 채점·피드백·담당자 파이프라인
```

### 7.3 `content_json` 에 들어가는 시나리오

```json
"scenario": {
  "situation": "노광 후 검사에서 웨이퍼 가장자리 쪽 패턴이 흐리게 나왔습니다. 중심부는 정상입니다.",
  "observations": [
    { "label": "패턴 상태",        "value": "중심부 정상 · 가장자리 흐림" },
    { "label": "직전 로트",        "value": "이상 없음" },
    { "label": "레지스트 도포 두께", "value": "기록상 정상 범위" },
    { "label": "평행도 점검 이력",   "value": "3일 전 수행" },
    { "label": "노광 시간",        "value": "설정값과 동일" }
  ],
  "checkItems": [
    { "id": "coat",     "label": "레지스트 도포 균일도 재확인" },
    { "id": "wedge",    "label": "마스크·웨이퍼 평행도(웨지) 점검" },
    { "id": "history",  "label": "장비 정비 이력 조회" },
    { "id": "focus",    "label": "노광 초점 설정 확인" },
    { "id": "contam",   "label": "마스크 표면 오염 확인" }
  ],
  "recommendedOrder": ["wedge", "focus", "contam", "coat", "history"],
  "orderNote": "권장 순서는 이 교육 과정이 정한 기준이며 모든 현장의 정답이 아닙니다.",
  "rationale": "가장자리만 흐리고 중심은 정상이라는 관측은 면 전체에 걸친 조건(평행도·초점)을 먼저 가리킵니다. 도포나 정비 이력은 관측이 그쪽을 가리킬 때 확인합니다."
}
```

**`rationale` 과 `recommendedOrder` 는 제출 전에는 화면에 보여주지 않는다.** 결과 화면에서만 보여준다.
`orderNote` 는 결과 화면에 함께 표시한다 — 우리가 정답을 확정하지 않는다는 표시다.

### 7.4 루브릭 4개 (`rubric_json`)

```json
[
  { "short": "관측 판독", "text": "관측값이 가리키는 곳을 먼저 확인하려 했는가" },
  { "short": "확인 순서", "text": "권장 절차와 가까운 순서로 배열했는가" },
  { "short": "범위 좁히기", "text": "상위 항목에 관련 높은 것을 모았는가" },
  { "short": "설명·기록", "text": "왜 그 순서로 확인하려는지 설명했는가" }
]
```

### 7.5 `scoring_metrics` (judgment 분석기가 만든다)

| 이름 | 뜻 |
|---|---|
| `firstPickRank` | 학습자가 1순위로 놓은 항목이 권장 순서에서 몇 번째인가 (1부터) |
| `orderDistance` | 각 항목의 (학습자 위치 − 권장 위치) 절댓값 합. 0이면 완전 일치 |
| `top3Overlap` | 학습자 상위 3개와 권장 상위 3개가 겹치는 개수 (0~3) |
| `answerLength` | 이유 글자 수 |
| `durationMs` | 소요 시간 |
| `passed` | `orderDistance <= 4` 이면 참 |

### 7.6 채점 규칙

| 기준 | metric | 방식 |
|---|---|---|
| 0 관측 판독 | `firstPickRank` | threshold — 1이면 2점, 2면 1점, 그 외 0 |
| 1 확인 순서 | `orderDistance` | threshold — 0~2면 2점, 3~5면 1점, 그 외 0 |
| 2 범위 좁히기 | `top3Overlap` | threshold, `direction: higher` — 3이면 2점, 2면 1점, 그 외 0 |
| 3 설명·기록 | `answerLength` | 정렬 실습과 같은 기준 |

### 7.7 답변 형태

```json
"answer": {
  "orderedIds": ["wedge", "focus", "coat", "contam", "history"],
  "reason": "가장자리만 흐리다는 건 면 전체 조건 문제로 보여서...",
  "submittedAt": "..."
}
```

`orderedIds` 는 `checkItems` 의 id 를 **빠짐없이 한 번씩** 담아야 한다. 서버가 검증한다(아니면 422).

## 8. 지켜야 할 것

- **정렬 실습의 동작과 점수가 바뀌면 안 된다.** 옮기는 작업이지 바꾸는 작업이 아니다
- 채점기 코드에 도메인 단어(`웨이퍼`, `정렬`, `overshoot` 판단 로직)가 남으면 안 된다
- 권장 순서는 **교육 과정이 정한 기준**이다. "정답"이라고 화면에 쓰지 않는다
- 판단은 학습자가 한다. 제출 전에 권장 순서를 알려주지 않는다
- 새 과정의 데이터·문구는 전부 `courses` 행 안에 있어야 한다. 컴포넌트에 쓰지 않는다

## 9. 단계와 컷오프

| 단계 | 내용 | 담당 |
|---|---|---|
| **A** | 채점을 `scoring` 데이터로 내린다 | BACK |
| **B** | `exercise_type` 도입, 분석기 분리 | BACK + FRONT |
| **C** | `judgment` 실습 구현 | FRONT + BACK |

**A → B → C 순서. 2일차 저녁이 컷오프다.**
C가 안 끝나면 버리고 A·B 로 발표한다. `defect-report` 를 다시 `coming_soon` 으로 되돌리면 된다.

## 10. 확정 이후의 결정 (2026-09-13 저녁)

A·B·C 구현이 끝난 뒤 올라온 것들에 대한 HEADER 판단이다.

### 10.1 `together` + 축 간섭 → **`capAt: 1`** (옛 동작 유지)

설계서 초안의 `adjust: -1` 로는 `convergenceOrder = together`(1점)에 축 간섭이 겹칠 때
0점이 된다. 0점은 "수렴 실패·판정 불가"와 같은 등급인데, 이 경우는 어쨌든 허용 범위에 들어왔다.

그리고 `together` 는 이미 "축이 섞였다"를 반영한 점수다. 축 간섭은 **같은 현상의 다른 측정**이라
두 번 깎는 것이 된다. 기준2에서 이미 "같은 것을 두 번 깎지 않는다"를 원칙으로 세웠다(API명세서 11절).

→ 정렬 실습의 기준1 modifier 를 `adjust: -1` 에서 **`capAt: 1`** 로 바꾼다.

**이 변경은 `content_json` 한 글자다. 코드를 건드리지 않는다.**
이번 작업이 무엇을 바꿨는지 보여주는 가장 좋은 예이므로, 발표에서 이 사례를 쓴다.

### 10.2 `content_json.feedbackNotes` (BACK 제안, 승인)

"허용 오차는 과정 설정값이다", "권장 순서는 정답이 아니다" 같은 **표현 규칙**이
LLM 프롬프트 코드에 박혀 있었다. 과정 데이터로 내린다.
과정마다 밝혀야 할 한계가 다르므로 이게 맞다.

### 10.3 `checkItems` 순서 (HEADER 설계 결함 수정)

초안은 `checkItems` 배열 순서가 `recommendedOrder` 와 같았다.
그대로 두면 **화면을 열자마자 권장 순서가 노출되고, 아무것도 하지 않고 제출해도 만점**이다.
FRONT 가 발견했다.

→ 7.3절의 `checkItems` 배열 순서를 권장 순서와 다르게 바꿨다.
FRONT 의 `initialOrder`(과정 id 기반 고정 섞기) 코드는 **지우지 않고 남긴다.**
나중에 다른 시나리오를 추가할 때 같은 실수를 막는 이중 안전장치다.

> **2026-09-14 정정** — 바뀐 것은 이 문서뿐이었고 **서버 데이터에는 반영되지 않았다**(BACK 보고, HEADER 확인).
> `course_judgment.py` 와 DB 의 `checkItems` 가 `wedge,focus,contam,coat,history` 로 권장 순서와 같았다.
> 결정은 그대로다 → BACK 에 7.3절 순서(`coat,wedge,history,focus,contam`)로 반영 지시.
> 채점은 `recommendedOrder` 만 보므로 점수는 바뀌지 않아야 한다.
>
> 같은 날 10.1 도 적용됐다. 문서의 "기준1" 은 **조정 순서 기준(criterion 1, 루브릭 두 번째)** 을 가리킨다.

### 10.4 `scenario` 를 과정 응답 최상위로 (BACK 할 일)

지금은 `content.scenario` 안에만 있어서 프론트가 두 위치를 모두 받는 보정 코드를 두고 있다.
`alignment` · `control` 과 같이 최상위로 올린다. 올라가면 프론트의 보정 코드를 지운다.
